## Working behavior and architecture

`SaveReviewableApproach` nests the unchanged actual J03 save/ApproachPolicy inside the existing tenant transaction. Content, numbered review, supersession/audit and in-app delivery commit together. An unchanged save creates nothing. Replayed request keys return their original scoped receipt after current authorization; mismatched payloads and stale revision/decision tokens conflict. Only pending reviews transition; historical correction/approval records remain.

`StageSubmission` freezes actual configuration, answers and exact evidence before any category selection. The optional typed `ApprovedStageAssessment` binding checks the exact approved target/revision/fingerprint, tenant/Approach/stage/configuration/answers and completeness. Legacy calls and tests retain their original behavior. Manual rating follows independent review; there is no midpoint, exact score or aggregate. A real approved prior stage, even the lowest category, unlocks the next initial stage. Reassessment and replacing historical initial results are unavailable pending their policy.

Evidence is a submission/question/expectation -> specific DocumentVersion relation. Every write/approval rechecks the unchanged actual DocumentPolicy, scoped version, trusted owned synthetic receipt and actual bytes/hash. No scanner/cleanliness, institutional document approval, general adequacy from counts or file serving is claimed. A human reviewer judges the bounded submission. Current loss of version access denies approval and redacts the inaccessible historical identity in UI while preserving SQL history.

In-app notices are themselves the delivery store in the origin SQL transaction: rollback leaves no delivery and no afterCommit crash-loss gap. Only the named current independent reviewer receives a new-review event; only the named current author receives the decision. Ineligible recipients get no substitute notice. Read state belongs to the current recipient and links reauthorize. No private content body is copied into a notice.

One unique `mvp_workflow_fixture` panel is explicitly registered only by the guarded test application. It uses original institutional login/provider/guard/password/session/membership and the real workflow Policy; nested actual J03/Document/workflow proofs share the same Request/PDO. Independent reviewer admission does not depend on J03 rights. `User::canAccessPanel()` remains unchanged and false for this test panel; no synthetic user or always-allow Policy is used. Normal providers, panels, routes, authentication and permissions configuration remain unchanged. Native DocumentResource is reused under its original actual DocumentPolicy.

Native Arabic RTL pages provide the assigned bank, content/decision/history, editable questions/scale, drafts with authorized version selectors, manual stage decisions, immutable assessment readback and notifications. Native Repeaters permit only exact nested form actions under a current configure-stage grant. Page-local DTO reuse ends with the request and is invalidated after mutations; it is never an authorization cache. Native split layouts improve small-screen history presentation.

## Database integrity, deployment and rollback

Actual compiled MySQL8.4.13 inventory: **40 migration files, 40 journal entries, 40 InnoDB base tables**. Eleven new migrations comprise two explicit candidate-key ALTERs and nine additive tables. Every tenant/resource/stage/revision/user reference uses the reviewed composite order and RESTRICT/RESTRICT. The executable schema gate checks exact columns/nullability, ordered FKs/full UNIQUEs, enforced CHECK clauses and stored expressions. Mutation tests require rejection of each missing/altered item.

MySQL's generated active slot enforces one pending review; numbered predecessor FKs prevent invalid chains. Assessment FKs bind the exact approved review/submission/reviewer; the ordinal predecessor enforces initial order. Exact positive24-hour expiry also rejects calculated-end overflow. JSON shapes/index consistency are DB-enforced; required inputs, current authority, evidence membership/bytes and human adequacy are application/domain responsibilities.

Each CREATE is one atomic statement and each candidate key has its own journal step. Actual missing-parent failures were exercised for all eleven; ordinary migration retry succeeds, and existing objects are rejected. InnoDB silently replaces original implicit child-FK support indexes when the covering keys are added. Reverse ALTERs restore the original two-column support index, when absent, atomically with removing the new candidate key. No parent data/column/applied migration changes or FK disabling occur.

Every down method scans all nine tables before its first destructive statement, refuses root-only/grant-only/populated history, checks owned shape/journal and rejects unknown external references. Candidate-key journal gaps fail closed. Empty dependency-order reversal is supported. DDL requires exclusive maintenance and the normal CREATE/ALTER/INDEX/FK privileges. Existing organizational-unit trigger deployment prerequisites still apply; no new trigger or global configuration is introduced. A crash between successful DDL and Laravel journaling requires operator inspection/forward recovery; automatic adoption/reset is deliberately unavailable.
