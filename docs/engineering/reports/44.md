## Implementation and boundaries

### Panel and identity candidates

Native Panel factories define two logical interfaces in one Laravel application. The platform candidate has no resources; the institution candidate explicitly lists one Approach Resource outside existing admin discovery. Both reference the existing theme and the exact existing native primary palette, ordinary cookie/session/CSRF/session-auth middleware and persistent Filament Authenticate middleware. Neither has login configured or a registered provider. Normal `Filament::getPanels()` still contains only admin.

Existing User rejects every user on the unregistered panels, and permits legacy/admin only in local/testing. Existing institutional/platform principals remain excluded from admin. Platform guard is deliberately absent from configuration. The new provider is tested directly, never registered with Auth: it filters persisted platform type + null binding, normalizes contact using the existing normalizer, rejects extra credential authority fields, and refuses ID/remember restoration without a platform marker or with leftover institutional scope. This is **not** a completed three-guard browser transition/login solution.

### Scoped application adapter and Policy

Pages contain presentation/configuration and call the small `ApproachAccess` application adapter. Domain validation, persistence, ownership and audit remain in CreateApproach, ListApproaches, UpdateApproach, ChangeApproachOwner and SaveApproachContentRevision. No generic repository/permission engine or duplicate domain implementation was introduced.

The adapter obtains the actor from the **institution guard**, reloads through the current provider, verifies principal/session marker, stored organization public ULID and password freshness, and establishes/restores TenantContext for each operation. It never accepts an actor or organization input parameter. It invokes the existing Approach transaction boundary, which locks current organization/user/membership, then scopes and locks the persisted resource and invokes Policy **before** calling the existing Action inside that transaction.

The Policy requires the existing TenantAuthorization predicate for an intentionally **unregistered** capability and an independent operation/resource assignment. Its shipped assignment predicate is always false. Standard unknown Gate abilities are denied; no global Gate-before allow or production-facing environment/config test bypass exists. The local/testing runtime restriction only narrows access. Synthetic test setup registers a structural capability and a test-only Policy subclass with explicit actor/action/resource grants; no application provider selects it.

The test-only list grant is explicitly institution-wide list metadata, separate from resource detail/mutation/history grants. This is a simulation contract, **not an approved D002 list policy**. Owning-unit membership, creation and read metadata confer no resource assignment. Actual future assignment persistence/expiry/delegation/SoD and query-level list scope require owner ratification and reviewed integration; none is invented here.

### ULIDs, conflicts and history

Table keys/route resource/owner options use public ULIDs; no Eloquent record is serialized into Livewire. List records are minimized to visible metadata. The workspace resource property is locked, and backend checks still apply to every callback. Submitted hidden tokens are concurrency proofs, not authorization. Extra tenant/actor/internal-ID/status fields are rejected by existing domain contracts.

Metadata and owner edits use the existing server-generated edit token. A stale edit raises real ConflictHttpException409 and the transaction rolls back. The draft adapter compares the latest revision public ULID (or the initial `none` sentinel) under the **same organization lock** before calling the existing append Action. It does not replace/renumber an old revision. Real MySQL workers observed on separate connections waiting for that row lock with the same initial draft token produced exactly one201 and one409, one version1 and no spurious audit. Fault after insert rolls back; retry still produces version1.

Draft and audit reads require distinct grants. Native history tables are bounded to10/20 and render escaped allowlisted state. There is no review/approval/published content engine, no ordinary-reader draft fallback, no self-approval path and no fake Approved/Maturity value. Append-only guarantees are those of existing Actions/model events and restrictive schema; raw SQL/bulk/quiet/operator access is not WORM.

## Remaining risks, approvals and next integration

1. **D002:** ratify operation/resource/actual-user assignment, who appoints the first quality officer, delegated scope, expiry/revocation and independent reviewer. No speculative roles/seeded grants. A broad organization-wide list grant used in a synthetic test is not ratification of ordinary-reader visibility.
2. **Runtime identity/Panel approval:** separately review platform guard/provider registration, three-guard browser transitions, User predicates, CSRF/remember/session freshness/persistent Livewire entry ordering, host/HTTPS/session-cookie deployment requirements and exact panel-provider paths. Six proposed shared files were intentionally unchanged; any additional path needs its own amendment. Do not just register these Panel factories.
3. **Actual grants/state:** future grant/assignment mutations must share a reviewed transaction/locking protocol with writes and list scope, including permission-definition revocation under old snapshots. Synthetic assignment maps are not durable, delegated or production-safe grant storage. Default-deny shipping makes no operational guarantee based on them.
4. **Read locking/performance:** this adapter deliberately reuses the conservative organization-row boundary for reads and authorization as well as writes. Multiple native visibility checks add queries/locks. No production latency/throughput/SLA or new no-N+1 claim is made; profile realistic assigned-resource listing and P95 after the approved authority/query contract.
5. **Owner selector:** existing ownerOptions is bounded to100 per page; current native Select uses its first page. A scalable authorized picker beyond100 units is a documented integration dependency, not an assertion that every institution fits100 units. Backend scoped validation still rejects any foreign/numeric owner.
6. **Publication/review:** actual approved-published pointer and immutable Review target/decision engine must precede ordinary content release. Supporting editing never grants approval; no self-approval emergency bypass. Preserve snapshots/versions when adding future review and evidence linking.
7. **Owner/ops:** D003/014, file scanning/quarantine/residency/retention/recovery and Issue13 remain blockers for their dependent features. Existing historical trigger privileges/binlog prerequisites still apply to any separately reviewed deployment; no global DB configuration changes here.

No deployment procedure is authorized by this Issue. Removing the unregistered candidate files reverts this preparation without DB rollback; a future release has its own migration/operator/backup/security review. Do not activate by toggling an environment flag or binding the synthetic test Policy. No real owner/tenant material is in the public diff.
