## المخطط والقراءة

| الجدول | العقد الفعلي |
|---|---|
| documents | BIGINT داخلي وULID فريد؛ organization/creator FKs مع RESTRICT؛ title255 وdescription LONGTEXT وcreated_at؛ UNIQUE(org,id) وفهرس(org,created_at,id) |
| document_versions | ULID مستقل؛ root FK وcomposite(org,document) وactor FK كلها RESTRICT؛ version unsigned32 ضمن1..4294967295 وUNIQUE(document,version) |
| بيانات التخزين | key فريد، disk محصور في local، SHA256 صغيرة الأحرف بطول64، byte_size غير سالب؛ original_filename للعرض فقط وdetected_media_type اختياري وغير مستخدم |

لا owner أو status أو updated_at أو softdelete أو EvidenceLink. الأسماء غير فريدة عمدًا. النماذج guarded وترفض التعديل والحذف العاديين، وتخفي معرفات الربط وبيانات التخزين. لا يُستخدم model serialization بوصفه عقد عرض عام.

ListDocuments يقدم بحث عنوان مع تهريب LIKE، وفرز title/created_at، وصفحات محصورة، وعدد الإصدارات وآخر رقم عبر استعلامات فرعية مقيدة بالمؤسسة دون N+1. ReadDocumentHistory يعيد تاريخًا حتى20 إصدارًا في الصفحة. لا BIGINT أو بريد أو filename أو hash أو key أو bytes في إسقاطات العرض. تحقق السلامة الداخلي يعيد digest/size فقط بعد إعادة تحميل النسخة المقيدة وإعادة فحص العضوية بعد I/O.

القراءات داخل snapshot خارجية قديمة قد ترى metadata قديمة، أما قرار العضوية والربط فيستخدم locking reads حالية. لا تُدعى صلاحية مستخدم نهائية لمجرد نجاح حد داخلي موثوق.

## تدفق الكتابة والتعويض

1. ترفض الكتابة خارج local/testing، أو داخل outer transaction، قبل كتابة البايتات.
2. يتحقق حد خاص بالوثائق من المؤسسة ثم الحساب ثم العضوية بالأقفال الحالية، دون توسيع CreateApproach أو إطار التفويض المشترك.
3. يقبل Action تدفق php://memory أو php://temp اختباريًا غير فارغ من بدايته. UploadedFile والمسار والنص البديل وحقول السلطة والتخزين غير المسموحة مرفوضة.
4. بعد preflight تُحرر الأقفال. تحجز الخدمة key جديدًا حصريًا تحت ULIDs المؤسسة والوثيقة والإصدار مع عشوائية256-bit؛ لا يحدد اسم الملف مساره.
5. تُكتب البايتات على local الخاص ثم تُقرأ للتحقق من SHA256 والحجم، خارج أقفال كتابة SQL.
6. تعيد معاملة حالية التحقق من العضوية والمورد، ثم تحفظ الوثيقة وv1 أو الإصدارn+1 مع UNIQUE. البايتات المطابقة تنشئ إصدارًا وملفًا مستقلين؛ لا dedup أو no-op مفروضة.

التعويض يستخدم نفس Store instance التي تملك المحاولة، وينظف ملف المحاولة وحده إذا ثبت غياب صف الإصدار بعد فشل SQL. لا يمس v1. إذا فشل التنظيف يبقى الخطأ الأصلي ويُسجل احتياج استرجاع خاص. إذا كان COMMIT ناجحًا أو نتيجته غير معلومة، تُحتفظ البايتات بدل المخاطرة بحذف نسخة محفوظة، مع استمرار رفع الخطأ الأصلي وعدم الإبلاغ عن نجاح وهمي.

لا توجد معاملة موزعة أو ضمان ذري مطلق بين DB والملفات. قد يترك crash بعد كتابة blob ملفًا يتيمًا؛ ويحتاج COMMIT غير معلوم أو crash بين DDL وjournal إلى فحص مشغل. لا reconciler أو purge policy مخترعة. قفل المؤسسة واسع وقد يسلسل العمل؛ لا benchmark أو ادعاء انعدام deadlocks. حماية append-only تطبيقية، وليست WORM أمام raw SQL/bulk/quiet/operator.

## Filament والأمان البصري

المكونات الفعلية: Table/TextColumns وSplit/Stack المتجاوبة، Schema/Section/TextEntry، وTextInput/Textarea معطلة وغير dehydrated، وText وAction معطل ومرفوض صراحة. لا Resource أو Page أو navigation أو route أو provider جديد. لا حفظ UI أو FileUpload.

تأتي البيانات من callbacks لخدمات القراءة، وتُحصر الحقول دفاعيًا قبل وصول السجل إلى Filament. استُخدمت qep-preview والثيم الحالي وألوانه وخطه؛ لا CSS جديد أو تعديل للمعاينات أو واجهة CRUD مستقلة. الحالات الفارغة والخطأ والمنع وعدم التفعيل صريحة. لا صاحب وثيقة أو حالة اعتماد أو درجة وهمية.

Livewire harness موجود في ملف PHPUnit فقط. سياقه ومنحه الاصطناعية على الخادم وليست سياسة تشغيلية. Native Schemas تتضمن upload trait ضمنيًا؛ لذا يرفض harness بدء الرفع بـ403 أيضًا، ولا يسجل التطبيق أي مكون وثائق تشغيلي. غياب Policy لا يتحول إلى allow، والتلاعب بحالة النموذج لا يغير DB أو ملفًا.

عُرض HTML الناتج من render الحقيقي، مع CSS المشروع وFilament/Livewire الأصلي، على static loopback فقط دون Livewire JS أو endpoint تشغيلي. القائمة والسجل عند375، والتفاصيل عند768، والنموذج عند1280 أظهرت scrollWidth مساويًا لعرض الشاشة وRTL صحيحًا. راجعت الصور؛ Tab يصل إلى input وتظهر حلقة تركيز أصلية2px على fi-input-wrp. هذا فحص أساسي، وليس تدقيق WCAG كاملًا.

الدعم الموجود لتوقيع خدمة local disk لم يتغير، ولم تُنشأ signed URL. معرفة key أوULID وحدهما ترفض الوصول. مراجعة file-serving والتفويض والفحص الإنتاجي ما زالت مطلوبة مستقلًا.

## متطلبات النشر والمخاطر والبوابات

MySQL ينشئ كل جدول في CREATE واحد بقيوده وفهارسه، وSQLite يستخدم DDL transaction. فشل FK لا يترك جدولًا جزئيًا؛ الجدول السابق الوجود لا يُتبنى أو يُحذف تلقائيًا. newest down يرفض قبل أول DROP مع أي وثيقة أو إصدار، حتى identity-only. اختُبر التراجع الفارغ وإعادة التطبيق.

يلزم لاحقًا MySQL8.4/InnoDB وenforced CHECK وصلاحيات DDL/REFERENCES/INDEX، مع مشغل ترحيلات منفصل لمتطلبات triggers/binlog السابقة وحساب runtime محدود. لا SUPER grant أوSET GLOBAL أوتعطيل FK أوترحيل لبيانات تطوير أوإنتاج. performance_schema مستخدم لرصد الأقفال اختباريًا فقط.

التراجع الممتلئ يحتاج backup وصيانة حصرية توقف جميع الكتابات وخطة forward recovery مراجعة. فحص وجود الصف ثمDROP ليس بروتوكولًا لحركة إنتاجية متزامنة. crash بينDDL وjournal أوcommit ambiguity يحتاج فحصًا، ولا يُعالج بمسح آلي.

التكامل اللاحق يتطلب اعتماد G2 ومعنى المالك ونطاق الإسناد والسحب وتحقق التفويض داخل حد المعاملة، ثم D007 للملفات والفحص والحجر والتنزيل، وD006 للاعتماد المستقل عن قبول الشاهد، وD008 للاحتفاظ والاستضافة والاسترجاع، وD027 للروابط، وG3/Issue13 للإنتاج. نجاح A أوتهيئة B لا يفتح أيًا منها.
