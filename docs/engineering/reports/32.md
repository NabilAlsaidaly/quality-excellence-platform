## Correction A — supported email addresses

Retained shared LoginEmail behavior for new institutional/platform principals: printable ASCII, trim outer ordinary spaces, lowercase complete address, validate syntax/maximum254 bytes, reject control/internationalized input. Creation/update, credential lookup, recovery lookup and throttle normalization are consistent. Dot/plus punctuation remains significant; there is no provider-specific alias rewrite or IDNA conversion. Existing same-institution duplicate/platform-namespace rejection and cross-institution reuse are preserved. Legacy email strings are never normalized or backfilled.

This is an **MVP technical constraint, not an independently approved permanent product policy**. Full local-part folding is not a universal mail-equivalence rule: SMTP permits case-sensitive local-parts, so case-distinct delivery systems are unsupported by this candidate. Retaining it matches the explicit case-insensitive candidate namespace and existing MySQL collation without a new identity model/package. Later onboarding/production support must review this limitation; extending supported addresses requires a separately reviewed contact/login-key design. See [RFC5321 §2.4](https://www.rfc-editor.org/rfc/rfc5321.html#section-2.4). No actual SMTP delivery is claimed.

DB CHECKs enforce lowercase ASCII for new principals and namespace uniqueness; they are not a full email-syntax grammar. Application normalizer validates syntax. Added regressions cover14 malformed/control/internationalized addresses across creation and lookup on SQLite/MySQL, uppercase lookup/update/recovery, no dot/plus collapsing, generic invalid recovery/login responses, and byte-preserved mixed-case/Unicode legacy contacts. No schema or data change is needed for this correction.

## Correction B — one active account context per browser session

New BrowserAccountSession has one concrete responsibility, using existing Laravel SessionGuard/Login events. No package, panel redesign or global default-guard switch.

| Trigger | Implemented behavior |
| --- | --- |
| Validated institution login attempt, including wrong credentials/throttle | End BOTH current-device guards, invalidate old session, regenerate CSRF and clear TenantContext before attempting credentials. Invalid-CSRF/invalid-form requests do not reach this Action |
| Successful explicit web or institution login | Laravel Login listener retires the opposite guard, removes stale institutional/intended state and marks the active guard. Normal SessionGuard regenerates ID/CSRF. Listener uses the actual guard session store, including real Filament/Livewire updates |
| Session-ID/remember restoration | Both providers refuse restoring the opposite guard while a context is active. Fresh credential validation remains available for an explicit transition; equal email never links identities |
| Protected institutional request | Require institutional marker, selected organization, fresh password/binding/membership and self-account Policy; clear context/relations in finally. Foreign/revoked/stale/old-unmarked sessions fail closed |
| Institutional logout/failed protected request | logoutCurrentDevice for both guards, clear current session/cookies and regenerate ID/CSRF; no stored remember-token rotation or deletion of unrelated sessions |
| Password reset | Existing intentional password/remember-token change remains; other independent accounts are untouched. Old institutional password snapshots fail on next request |

A separate clean browser can still use its own valid legacy credentials/remember cookie. This contract does not claim revocation of a copied valid remember credential in an unrelated clean session without rotating its token. Within an active institutional context, that legacy credential cannot silently restore admin access. An old candidate session lacking the new marker must explicitly reauthenticate. Context is verified per request; no tenant-content capability, administrative bypass, invitation, account management or document approval is introduced. Existing production/staging entry/panel denials remain.

13 new guard-transition cases exercise both real guards and the actual Filament Login Livewire component, legacy→institution and institution→legacy transitions, failed/revoked/forged/throttled attempts, injected guard ID and valid recaller, old sessions, current-device logout, retained other-browser recall, real CSRF rotation/rejection, password change, membership revocation and cross-institution route denial. Initial10 security cases failed against the prior code; after correction they passed, and the full135-test SQLite suite passed with all original cases intact.

## Architecture and five-migration review

Independent institutional accounts retain users.id, distinct credentials/verification/remember state and public ULIDs. Existing users remain explicitly legacy with zero/one/multiple memberships; there is no mapping by email, automatic account merge or copied grants. Platform is an explicit isolated namespace, not inferred from NULL or granted tenant membership. Legacy email-only provider excludes new institution/platform principals. Institution provider/guard and account-keyed Laravel broker handle selected institution plus current persisted membership.

Recovery stores hashed tokens by account/organization with current contact/password digest and a restrictive composite FK. Current User/membership/token locking reads serialize issue/consume under old InnoDB snapshots; expired/replayed/foreign/revoked/contact-changed tokens fail. Signed account/institution routes use trusted APP_URL, Host validation, generic feedback, scoped throttles, safe redirects and no-store/no-referrer. Notifications are after commit and faked in tests; no real mail sent. Minimal Arabic RTL login/recovery/reset/account/logout remains local/testing only, including runtime environment denial after route caching. No institutional Livewire domain component is added; existing Filament authentication is now explicitly transition-tested.

All five candidate migrations were re-read; **none changed in this correction**. Earlier applied migrations remain unchanged too.

| Candidate migration | Integrity, journal and rollback review |
| --- | --- |
| 000001 users expansion | One atomic MySQL ALTER replaces global email uniqueness together with generated namespace/email uniqueness, public ID and ordered `(id,organization_id)` keys, principal shape/lowercase-ASCII CHECKs and unsigned root RESTRICT FK. Explicit platform/legacy namespaces avoid the multiple-NULL uniqueness hole; SQLite equivalent is transactional |
| 000002 membership INSERT guard | One CREATE TRIGGER per journal entry rejects platform membership or unrelated institutional scope; down refuses existing nonlegacy principals |
| 000003 membership UPDATE guard | Same scope enforcement on mutation, including paths feeding existing composite role/direct-permission pivots; independently journaled and guarded down |
