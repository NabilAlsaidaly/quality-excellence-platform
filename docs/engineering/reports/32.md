## Actual implementation

See [architecture](../../architecture/institution-identity-entry.md) and [proposed ADR](../../adr/ADR-004-institution-identity-candidate.md). Retained users.id now has explicit legacy/platform/institution shape, immutable public account/institution binding, generated non-null logical namespace and namespace/email uniqueness. Legacy records stay unmapped; new principals cannot enter old email-only web/Filament resolution. Platform is an isolated namespace with no new entry/grant. ASCII mailbox/domain canonicalization is explicit; Unicode input is rejected, historical contacts untouched.

Laravel institution guard/provider handles independent credentials; request middleware reloads identity, checks session scope/password and current membership, enters/clears TenantContext and applies a self-account Policy. No domain capability is registered. Session regenerates at login; logout invalidates session/CSRF; remembered context, foreign route, stale credential or removed membership cannot substitute for login. New routes are local/testing only, including runtime checks after route caching. Production/staging panel denial is retained.

Recovery uses the Laravel broker with account-keyed hashed tokens, composite account/organization FK and contact/password digest. Current account/membership/token locking reads serialize issuance/consumption and defend old snapshots. Real contact addresses remain notification destinations; signed account/organization routes use configured APP_URL, not request Host. Generic responses, scoped throttles, expiry/replay checks, remember-token rotation, host validation, safe redirect targets, no-store and no-referrer are implemented. Notifications are after commit; automated transports are faked, no real mail delivered or claimed.

Routes: GET/POST `/institution/login`; POST `/institution/recovery`; GET/POST `/institution/{organization}/reset/{account}/{token}`; GET `/institution/{organization}/account`; POST `/institution/{organization}/logout`. All use normal web CSRF/session middleware. No institution directory or account provisioning endpoint. Landing exposes the current account greeting only. Existing admin dashboard/login/logout remain intact and separately guarded.

## Migration/history and rollback

Five new migrations; original applied migrations unchanged. The MySQL users expansion is one atomic ALTER combining columns, namespace replacement uniqueness, shape/email CHECKs, root FK and candidate/public keys. SQLite changes are transactional. Each of three new narrow triggers is one CREATE in its own journaled migration; a denied CREATE cannot leave half of a multi-trigger migration. The reset table is one CREATE with inline composite RESTRICT FK. No FK disabling or global setting change.

Existing User actor/subject IDs, membership/role/pivot FKs and historical rows are preserved. Legacy zero/one/multiple membership behavior remains only in the old internal foundation and is excluded from new entry until explicitly mapped. No actual application/production row inventory, mapping or migration was performed. Populated synthetic MySQL tests exercise legacy/history preservation, failed atomic ALTER/ordinary retry, rollback refusal, revoked old snapshots and two-process token contention; current results are below.

An exclusive maintenance cutover and separately authorized real inventory/backups are prerequisites for any later deployment. Do not run the old email-only binary while new namespace data exists or permit concurrent account writes during incomplete migrations. DDL success/journal-insert process death remains an operator-inspection window: unjournaled existing expansion is refused, never adopted/dropped blindly. Down refuses nonlegacy account semantic loss or live reset state. Empty/legacy-only fixtures roll back/repeat; after new semantics exist, prefer a reviewed forward correction. Never delete equal-email principals/history to make rollback work.

The schema gate explicitly adds the new direct reset table and User nullable binding/keys/FK. Original negative integrity assertions remain. Exact journal-count expectations change14→19 (or13→18 after removing one); old history/permission rollback path/steps still exercise their original targets. Users is now asserted as mixed principal storage with nullable binding instead of incorrectly asserting the column absent. No test is skipped/weakened to obtain green.

Post-implementation review found that rejecting only the last reverse ALTER could allow earlier reverse steps to remove guards while accounts remained. The correction makes ordinary rollback refuse at its first reverse migration for ANY nonlegacy principal, including when there are no tokens, and makes each trigger down independently refuse. The MySQL regression invokes ordinary rollback, checks all19 journal entries and all three guards remain, and directly exercises all five refusal boundaries. Exclusive maintenance writes remain required.
