## 1. النتيجة وسلطة القرار

**Workstream A منفذ ومختبر داخل الحد الداخلي الموثوق. Workstream B إعداد قابل للاختبار لكنه BLOCKED تشغيليًا.** تعديل البيانات ونقل المالك أصبحا ذريين ولهما سجل مستقل، بينما لا يوجد تفويض مالك نهائي يجيز تشغيل مسارات المستخدمين. نجاح الاختبارات الاصطناعية لا يصنع هذا التفويض.

التتبع: BR001..006، FR-APP001..008/010 ومعايير AC المقابلة. تمت مراجعة SRS المعتمد ومصادر المالك ذات الصلة، ADR001/002/003 المقبولة، ADR004 المقترحة، decision-ledger، Issue12/13/37/40، وتطبيق38 الحالي. لم تتغير نسخة SRS عن المراجعة السابقة، وتطابق tree الأساس مع النسخة المراجعة أعيد التحقق منه، مع قراءة الملفات المتأثرة وحدود الهوية/التفويض مجددًا. أدلة النسخ والبصمات خارج Git.

D002 لم تُصادق كمصفوفة عملية/مورد/assignment؛ المقترح السابق لا يُنفذ كسياسة. لم تُكرر أسئلة D021 أو حقول المنهجية أو المالك الواحد المحسومة. لا تغيير للهوية أو SRS أو ADR مقبول. الإذن التقني لا يملأ سياسة مالك مفتوحة.

التباس scope في AT-A03 وُثق قبل الكود: scope الوصفي مسموح صراحة في A1، أما نطاق التخويل وorganization/actor/identity injection فمرفوض. تكرار تعليمات الفرع الموجود مقدم على السطر العام عن فرع جديد؛ استُخدم فرع40 نفسه.

## 2. السلوك وحدود الواجهة

- UpdateApproach يقبل فقط name/description/purpose/scope/objectives/review_frequency. يرفض unknown keys، الفراغات الإلزامية وUTF-8 غير الصحيح والتجاوزات التقنية. الأهداف ودورية المراجعة يقبلان null. لا قص أو تفرد أسماء أو سياسة أعمال مستحدثة.
- ChangeApproachOwner يقبل ULID وحدة أخرى داخل المؤسسة نفسها، يسجل المالك السابق والجديد مع أسمائهما التاريخية، ولا يغير creator أو هوية المنهجية أو محتوى النسخ أو أدوار المستخدمين.
- كلاهما يستعملان boundary المعاملة والعضوية الحالي الموجود دون تغييره، ويقرآن الحالة الحاضرة بالأقفال، ثم UPDATE مؤهل بالمنهجية والمؤسسة وINSERT حدث مستقل. الفشل عند طرفي INSERT يلغي كل الكتابات.
- edit_token يُفحص بعد القفل؛ نقصه/تشوهه422، تقادمه409 دون overwrite. البصمة تتضمن أحدث event ULID فتمنع ABA عند عودة القيم. no-op مع proof حاضر لا يكتب حدثًا أو updated_at.
- ListApproaches يضيف proof لshow فقط، وقراءة audit بصفحات≤20، وownerOptions بصفحات100. النتائج arrays محددة لا BIGINT/contacts/raw payload. قراءة المحتوى منفصلة ولم تُوسع.
- بقيت Approach ordinary update/delete guards، وكذلك CreateApproach وApproachContentRevision وSaveApproachContentRevision والترحيلات السابقة كما هي.

Controllers وFormRequests والقوالب موجودة دون registration. **لا مسار Approach فعلي في route collection، ولا ApproachPolicy أو capability أو role/grant جديد.** لذلك لا روابط لصفحات غير متاحة في واجهة التطبيق الحالية. operational=false هو الافتراضي في القوالب؛ المسارات والPolicy/grants الإيجابية محصورة داخل PHPUnit.

عقد Policy المقترح للـadapters: viewAny/view/create/updateMetadata/changeOwner/editDraft/viewDraftHistory/viewAuditHistory. هذه أسماء عمليات لا مصفوفة أدوار معتمدة. كل request يفحص institution guard وTenantContext الحالي وGate قبل القراءة أو Action. غياب Policy يرفض403. resource lookup مؤهل بالمؤسسة؛ foreign/missing404 عند السماح بالعملية و403 عند رفض Policy. لا يُثق actor/org من body/query. InstitutionSession وauth/registry/providers/routes لم تتغير.

FormRequests تحصر الصيغة والمفاتيح؛ Actions تعيد تحقق الحقيقة داخل المعاملة. CSRF من middleware الحقيقي، redirects نسبية ثابتة لا Referer، confirmation صريح لنقل الملكية، وproof الأصلي يبقى بعد validation redirect لمنع إعادة تأسيس نموذج قديم فوق تعديل متزامن. Blade يهرب النص وRTL وlabels عربية، وأي حفظ يبقى غير معتمد وغير منشور.

## 5. قاعدة البيانات والأمان والاسترجاع والمخاطر

approach_changes ذو BIGINT داخلي وULID فريد، org/approach/actor RESTRICT، composite old/new unit references داخل المؤسسة، JSON object/event/owner-shape CHECKs، created_at فقط وفهرس(org,approach,id). physical migration inventory22/journal22/24tables verified؛ لا global schema exception.

current lock order يبدأ organization→actor→membership ويقفل المورد والمالك قبل proof. snapshots metadata كاملة وowner labels تاريخية. ordinary model guards محفوظة، ولا side effects على content/roles. قفل المؤسسة واسع وقد يقلل throughput، ولا يضمن غياب deadlocks أمام كتّاب خام غير متعاونين. قوائم MVCC قد ترى snapshot خارجية قديمة؛ القرارات الأمنية والنسخة تستخدم current reads.

MySQL DDL CREATE واحد مع كل القيود والفهرس، وSQLite table+index transaction. فشل FK أو index لا يترك جزءًا؛ جدول موجود لا يتبنى/يحذف. down الجديد يرفض قبل FIRST DROP مع أي Approach/Revision/Audit، حتى identity-only. empty rollback/reapply مختبر. populated recovery يتطلب backup وخطة forward مستقلة ومراجعة، لا حذف لتحقيق نجاح rollback.

متطلبات نشر لاحق: MySQL8.4/InnoDB وJSON/enforcedCHECK وDDL/REFERENCES/INDEX privileges، مع migration operator مخول للـtriggers/binlog في الترحيلات السابقة. احتمال1419 ما زال يُختبر فعليًا، لا SET GLOBAL ولا حذف integrity guarantees. حساب runtime منفصل محدود؛ performance_schema امتياز اختباري لرصد الانتظار فقط. maintenance حصرية توقف جميع الكتابات قبل rollback؛ وجود-row-check ثمDROP ليس بروتوكول تزامن لحركة إنتاجية.

المتبقي: crash بعدDDL وقبلjournal يحتاج فحص مشغل ولا retry يتبنى/يمسح الجدول تلقائيًا. append-only تطبيق/model وليس WORM؛ raw SQL/bulk/quiet أو DBoperator يمكنه تغيير بيانات متوافقة، والـCHECK لا يثبت صدق JSON. audit خاص بالمؤسسة ولا تمنح platform access. لا تغييرات على dev/prod DB أو guards/config/CI/packages.
