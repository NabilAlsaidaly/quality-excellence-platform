## One transaction / lock protocol to implement after approval

The common serialization prefix is **Organization X → sorted User IDs X → sorted membership IDs X**. Supported unit, role/permission and Approach writers acquire that prefix before authorization or any domain/role lock, on one PDO connection/outer transaction held through audit and commit. A nested existing Action may reuse the same locks/savepoint; it must not commit/release the outer boundary. J03 already has the single-actor prefix; RoleManagement is the incompatible current participant. Identity-only recovery currently takes User→membership and never later requests Organization, so its locks serialize through the same User/member suborder without an organization-order inversion; fresh session hash must still be checked after waits. No recovery source amendment is claimed necessary from current evidence.

After the common prefix, keep the concrete domain order: Approach resource then Policy role/pivots then assignments; units authorization then their existing target/parent/ancestry locks; roles scoped definitions/pivots. Different suffixes within the **same organization** cannot race once every supported writer holds its organization mutex. This does not pretend the optimizer locks joins in the written SQL order. Multi-user lock sets must be sorted before membership acquisition; no late second User after locking another actor's membership. Unit ancestry need not be broadly rewritten to sorted traversal: existing organization mutex protects it among supported writers. Raw external/uncoordinated SQL is outside the guarantee.

Current structural query shape (all values server-bound, no user authority IDs):

```sql
-- In the existing outer mutation transaction, after trusted scope resolution:
SELECT id FROM organizations WHERE id = :trusted_org FOR UPDATE;
-- Actor + subject, if any: individual PK reads in ascending numeric order.
SELECT * FROM users WHERE id = :trusted_user FOR UPDATE;
SELECT id FROM organization_memberships
 WHERE organization_id = :trusted_org AND user_id = :trusted_user FOR UPDATE;

SELECT mr.role_id
 FROM model_has_roles mr
 JOIN roles r ON r.id = mr.role_id AND r.organization_id = mr.organization_id
 JOIN role_has_permissions rp ON rp.role_id = r.id
 JOIN permissions p ON p.id = rp.permission_id
 WHERE mr.organization_id = :trusted_org
   AND mr.model_type = :user_model AND mr.model_id = :trusted_actor
   AND r.guard_name = 'web' AND p.guard_name = 'web' AND p.name = :recognized_capability
 FOR SHARE;
-- Domain mutation, original audit, final validity recheck, outer COMMIT.
```

Actual EXPLAIN on MySQL8.4.13 for the bounded join chose **p → mr → r → rp**, including the permission name/guard unique key and existing scoped indexes. Real locking execution returned currentfalse after revokes/currenttrue after grant while equivalent snapshot/outer-EXISTS stayed old. No schema/index change is demonstrated necessary. Preserve the full plan privately; do not promise a permanent optimizer plan or bound locks to returned rows only. The common organization row, not a presumed join order, is the coordination point. See [MySQL locking reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html) for nested locking-clause/current-read semantics.

Linearization/acceptance: revoke commits first → fresh post-lock authorization denies with zero domain/success-audit changes; writer acquires mutex first → writer may commit, then revoker commits, then every later mutation denies. New permission grant must be observed by the transactional structural decision even with a prior RR snapshot; outside-transaction display hints can remain conservative. Recheck password and applicable assignment expiry after lock waits and before commit. No bypass after SQL error. Deadlock1213 and timeout1205 must escape the one-attempt mutation and roll back its **whole application transaction**, not merely the last statement or a savepoint followed by continued success. No automatic write retry, SKIP LOCKED grant fallback, fairness guarantee or SET GLOBAL. [MySQL deadlock handling](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks-handling.html) recommends consistent ordering; [error handling](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html) distinguishes deadlock and timeout rollback scope. The no-retry disposition here is this Issue's engineering contract, not a claim that the manual forbids retries.
