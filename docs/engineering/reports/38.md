## 4. المخطط وسلامة البيانات

ترحيلان إضافيان فقط: approaches وapproach_content_revisions. BIGINT UNSIGNED داخلي وULID فريد خارجي. approaches يحفظ organization_id/owning_unit_id/created_by والبيانات الأساسية والأهداف/الدورية الاختيارية والوقت. FK المالك **مركب فعليًا** إلى organizational_units(organization_id,id) الموجود والفريد، وليس FK مستقلًا يُخلط بضمان العزل. لا تفرد للاسم، وتسمح الاختبارات بتكراره داخل مؤسسة وبين مؤسستين.

الإصدارات تحمل organization_id/approach_id/actor_id/version_number/body/created_at وULID مستقلًا. FK مركب إلى approaches(organization_id,id)، وUNIQUE(approach_id,version_number)، وCHECK لرقم موجب ضمن unsigned32. كل مراجع الأصل والفاعل والمالك والتاريخ RESTRICT. لا cascade يمسح نسخة أو تاريخًا.

ست علاقات FK جديدة وقيودها فُحصت فعليًا على MySQL. المخطط مصنف مباشرة في السجل التنفيذي، وتُرفض إزالة علاقاته أو مفاتيحه أو تغيير type/nullability/range أو إدخال cascade في fixtures metadata سلبية. لا مرجع nonunique مهمل في MySQL8.4، ولا تغيير لاستراتيجية المعرفات.

فهارس القائمة (organization_id,created_at,id) و(organization_id,name,id) تدعم الترشيح والفرز المحددين. البحث المحتوي على wildcard بادئ ليس ادعاءً لفهرسة النص أو قياس أداء. لا N+1 للمالك. قيود الحجم تقنية قابلة للمراجعة: الاسم255، النصوص الوصفية65535، body مليون محرف، لا سياسة مالك رقمية مستنبطة. UTF-8 والفراغ يتحققان في Action نفسه دون الاعتماد على FormRequest.

اختير نص مسودة عادي بدل JSON بأقسام مُصدرة، بعد توثيق البديلين وحدود تطورهما قبل كتابة المخطط. لا يُفرض قالب سياسات/إجراءات/مؤشرات ولا محرك نماذج. النصوص تعرض escaped وتحفظ bytes دون استبدال النسخة السابقة.

## 5. المعاملات والأمان والتاريخ

تُجمد معرفات السياق والفاعل الموثوق، ثم تقرأ المؤسسة والفاعل والعضوية حاليًا بـFOR UPDATE، قبل الوحدة أو المنهجية. الكاتب المسجل يأتي من صف User المعاد تحميله، لا من actor_id في payload أو نموذج قابل للتغيير. الحساب institution يجب أن يطابق المؤسسة، وplatform مرفوض. context أو membership المفقود/المسحوب يمنع القراءة والكتابة حتى إذا بقيت نسخة أقدم من العضوية في snapshot.

تُقفل المنهجية قبل تخصيص الإصدار، وأحدث نسخة تُقرأ بقفل حالي. اختباران/عمليتان حقيقيتان على MySQL يرصدان انتظار InnoDB فعليًا على صف المؤسسة عبر performance_schema، ثم يثبتان حفظ النصين برقمين مختلفين رغم snapshot أقدم. لا نعتمد على SQLite لمحاكاة FOR UPDATE. عدد محاولات transaction واحد؛ لا retry صامت أو I/O شبكي داخلها.

الفشل بعد INSERT يلغي الإصدار، ويمكن لمحاولة جديدة تخصيص الرقم الذي لم يُعتمد. rollback الخارجي يلغي الهوية والمحتوى معًا. حفظ النص المطابق يعيد النسخة السابقة دون تغيير مؤلفها/وقتها؛ ليس كل استدعاء حدثًا تاريخيًا جديدًا.

أحداث Eloquent تمنع تعديل/حذف Approach وRevision، لكن raw SQL/bulk/تعطيل الأحداث ليست تخزينًا محصنًا. يمكن لمشغل DML تغيير body أو حذف leaf revision أو إعادة إسناد هوية بلا نسخ إذا حافظ على جميع FKs؛ لا توجد له واجهة تطبيق معتمدة. DB يفرض الاتساق المرجعي وUNIQUE/RESTRICT، ولا يثبت وحده immutability أو صلاحية مستخدم. لا تدّعي هذه المهمة حصانة من مشغل DB. FK المؤلف إلى User عالمي تاريخي، بينما العضوية الحالية شرط Action؛ سحبها لا يمسح المؤلف.

قفل المؤسسة واسع وقد يسلسل عمليات المؤسسة. القوائم تحت snapshot قديمة قد تعكس بيانات MVCC أقدم؛ قرارات العضوية وتخصيص النسخة حاليّة. لا ادعاء throughput أو benchmark أو انعدام deadlock مع كتّاب خارج البروتوكول. المعرف العام ليس تفويضًا، والنماذج الداخلية ليست serializers عامة.

## 6. الترحيل والتراجع وقابلية النشر

MySQL: CREATE واحد inline مع القيود والفهارس لكل جدول، لا trigger جديد أو نافذة جدول بلا FK. SQLite: إنشاء approaches وفهارسه داخل transaction DDL واحدة. أُضيف اختبار تعارض اسم فهرس بعد CREATE للتحقق من إزالة الجدول الجديد تلقائيًا وبقاء الكائن السابق وإمكان retry. لا تبنٍّ أو DROP لجدول سابق عند خطأ existing-table.

التراجع الفارغ يعيد التطبيق. عند وجود هوية منهجية أو نسخة، يرفض الترحيل الأحدث **قبل أول DROP** حتى لو لم يوجد محتوى بعد، ويرفض ترحيل الهوية محو صفوفها. لا تنظيف بيانات حقيقية لفرض نجاح down. يتطلب DDL نافذة صيانة حصرية مع إيقاف الكتابات والنسخ الاحتياطي؛ فحص empty ثم DROP ليس آلية rollback متزامن أثناء حركة المستخدمين. التصحيح forward هو مسار المراجعة لاحقًا عند وجود تاريخ.

الانقطاع بين DDL ناجح وكتابة migration journal يظل مخاطرة مشغل تحتاج تحققًا، ولا نعالجها بحذف/تبنٍّ أعمى. متطلبات CREATE/REFERENCES وMySQL8.4 موثقة؛ متطلبات trigger/binlog للترحيلات القديمة مستمرة، دون SET GLOBAL أو تعطيل FK أو صلاحيات تشغيل عامة جديدة. لا تجربة على قاعدة التطوير أو بيانات المستخدمين.
