# ADR-004 institution identity candidate

**Status: PROPOSED — implemented candidate for independent review under [Issue32](https://github.com/NabilAlsaidaly/quality-excellence-platform/issues/32), not accepted or deployment-approved.** A limited successor/amendment to ADR-002 identity semantics; ADR-002 remains the historical accepted decision. Unaffected ADR-001/002/003 security and history guarantees remain mandatory.

## Context and authority

Received D-021 requirements and the explicit Phase05B-1 implementation contract authorize independent institutional principals, scoped entry/recovery and a branch candidate. They do not authorize operational D-002 grants, production access, source edits or self-acceptance of this ADR. Private source reconciliation is held in the ignored project-local handover. The canonical source is not amended.

## Proposed implementation

Retain users.id and all historical actor/subject relationships. Explicit principal_type is legacy, platform or institution; never infer platform from a NULL binding. Existing rows remain legacy without mapping/copying permissions. New institutional accounts have one organization binding, independent password/verification/remember state and public account ULID. New platform principals are isolated and have no new login/admin surface or membership grant.

A generated namespace plus email unique key separates institution, platform and legacy uniqueness. It replaces global email uniqueness atomically on MySQL. Platform uniqueness does not rely on nullable composite keys. New-account contact input is trimmed lowercase ASCII; internationalized mailboxes/domains are rejected, not silently folded or converted. Historical legacy contacts are untouched. Institution locators use the existing non-secret public ULID, canonical lowercase as generated by installed Laravel; no directory/discovery service is added.

Membership insert/update and account binding updates have narrow DB guards. Existing membership/role composite FKs and restrictive historical references remain. New reset tokens reference account+organization through a restrictive composite User key. No extra person/SSO/identity service or database split.

Use a separate Laravel institution session guard/provider, with current membership/binding checks. The existing web provider remains available only for legacy principals, excluding new institution/platform principals from email-only resolution. The institutional broker retains Laravel's broker contract but uses an account-keyed token repository. Contact delivery stays a real email address. Signed scope/account-bound links use configured APP_URL rather than incoming Host; token hashes also bind the current contact/password digest. Account/membership/token locking reads serialize issuance/consumption and reject stale-snapshot replay.

Minimal Arabic RTL login/recovery/reset/own-account/logout is local/testing only, including a runtime environment check against cached route registration. It grants no private institution-content capability and does not enable Filament access. Registry stays empty. A narrow Policy protects self-account/session information; future domain Actions/Policies remain gated.

## Alternatives and tradeoffs

- Shared global credentials plus membership switching contradict the received functional semantics; rejected.
- Forcing globally unique contact addresses would constrain approved reuse; rejected for this candidate.
- A global login handle with separate contact fields adds allocation/recovery rules without removing account-bound recovery; not selected.
- Separate authenticatable tables would complicate existing User actor/pivot FK compatibility; retaining stable User keys is the smaller candidate.
- Full Unicode/IDNA mailboxes, operational platform identity, invitations, lifecycle/management and delegation are intentionally absent, not silently implemented by namespace columns.

## Migration and rollback limits

Five new journaled migrations: atomic users ALTER; one membership INSERT guard; one membership UPDATE guard; one account-binding UPDATE guard; one atomic token-table CREATE. SQLite expansion/down uses transactions. Existing applied migrations and rows are not rewritten. Trigger privileges/binlog prerequisites remain; no server-global change.

Maintenance/exclusive deployment window is required: no new account writes or old email-only binary while expanding/cutting over. Before that window, inspect pending SQL, backups, target, privileges and separately authorized legacy inventory. Ambiguous legacy rows remain ineligible for institutional entry. One trigger per migration means denied creation leaves no multi-object partial migration; earlier successful migrations remain journaled. Process death between successful DDL and journal insertion still requires operator verification; do not adopt/drop an existing unjournaled expansion automatically.

Rollback refuses to discard nonlegacy account semantics or live institution reset tokens. The first reverse step checks account state even with no tokens; every guard migration independently refuses before removing integrity protection. Empty/legacy-only fixtures can roll back and repeat; after new semantics exist, old global-unique-email code/schema is unsafe and a reviewed forward correction is preferred. Never delete duplicate-email accounts/history or rewrite old actor IDs to make rollback pass.

## Acceptance and review

Require actual populated synthetic MySQL expansion, failed ALTER/retry, stable history/FKs, namespace/raw cross-tenant rejection, independent credentials/reset/session, real two-process token concurrency and unchanged full regression. See [architecture](../architecture/institution-identity-entry.md), [report](../engineering/reports/32.md) and the private project-local packet for evidence/limits. Lead acceptance, canonical reconciliation and any future D-002 grant ratification remain separate from IMPLEMENTED/TESTED status. No merge or production rollout by this ADR.
